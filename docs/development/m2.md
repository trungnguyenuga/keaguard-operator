# M2 development and local acceptance

M2 is an explicit opt-in fixed Kea process workload managed by a `KeaCluster`. It deploys two independent StatefulSet replicas, each running two real Kea daemons (one DHCPv4 container and one DHCPv6 container), with pinned ISC images, generated ConfigMaps, probes, and private ephemeral runtime files. It is a process-management demonstration, not a DHCP service: the generated configurations have no interfaces/subnets/pools/hooks or listener, the suite sends no DHCP packets, and M2 does not implement lease synchronization, Kea HA, or failover. Those behaviors are outside M2 and belong to the later M3 lab. A green Pod/process condition proves only the process/readiness contract.

The default sample remains metadata-only and disabled. The enabled [M2 sample](../../config/samples/infrastructure_v1alpha1_keacluster_m2.yaml) is deliberately not included by `config/samples/kustomization.yaml`; applying it is a separate administrator choice.

## Private lab identity and image evidence

M2 accepts only the dedicated cluster `keaguard-m2-disposable`, context `kind-keaguard-m2-disposable`, with one control-plane and two workers on the node pin above. Its task-local files are:

```text
/tmp/keaguard-m2-acceptance/keaguard-kind.kubeconfig  # regular file, mode 0600
/tmp/keaguard-m2-acceptance/docker-config             # private, mode 0700, empty during acceptance
/tmp/keaguard-m2-acceptance/docker-build-config       # separate private Buildx metadata directory
```

Never copy kubeconfig or Docker credentials into the repository. Do not use global Docker credentials or place build-generated Buildx state in the acceptance `DOCKER_CONFIG`. The guarded M2 build wrapper uses the sibling build config; acceptance refuses a populated, symlinked, foreign-owned, or otherwise unsafe config directory.

The manager tag is derived from a complete public-input manifest, not a hand-chosen version. From the repository root in Bash, the reviewed manifest format can be reproduced as follows; it includes cached and untracked non-ignored public inputs and excludes the private execution directory under `.gitignore`:

```bash
M2_DIR=/tmp/keaguard-m2-acceptance
git ls-files -z --cached --others --exclude-standard | sort -z |
  while IFS= read -r -d '' path; do
    printf '%s\0' "$path"
    sha256sum -- "$path" | awk '{print $1}'
  done > "$M2_DIR/inputs.manifest"
sha256sum "$M2_DIR/inputs.manifest" | awk '{print $1}' > "$M2_DIR/inputs.sha256"
chmod 0600 "$M2_DIR/inputs.manifest" "$M2_DIR/inputs.sha256"
FINGERPRINT=$(cat "$M2_DIR/inputs.sha256")
IMG="keaguard-operator:m2-${FINGERPRINT:0:12}"
```

On a fresh, private task directory, keep `DOCKER_CONFIG` empty and build with the reviewed IID procedure:

```bash
export DOCKER_CONFIG=/tmp/keaguard-m2-acceptance/docker-config
make docker-build IMG="$IMG" CONTAINER_TOOL=docker \
  BUILD_IID_FILE=/tmp/keaguard-m2-acceptance/manager-image.iid
chmod 0600 /tmp/keaguard-m2-acceptance/manager-image.iid
docker image inspect --format '{{.Id}}|{{.Os}}|{{.Architecture}}' "$IMG" \
  > /tmp/keaguard-m2-acceptance/manager-image.identity
chmod 0600 /tmp/keaguard-m2-acceptance/manager-image.identity
```

The IID, local Docker image identity, selected Linux/amd64 OCI manifest and config, node containerd content, CRI image status, and live Deployment/ReplicaSet/Pod/container must be attested as one chain. A tag, nonempty `imageID`, or equality between an OCI index digest and a config digest is not sufficient. `make test-kind` loads the selected image into the exact Kind cluster and the M2 suite independently checks the OCI/CRI chain before accepting the manager.

## Create-only lab setup and test commands

Use a dedicated disposable machine-local lab only. Never reset or delete a cluster to make these commands succeed. If the selected cluster already exists, inspect and verify it; `make kind-create` is only for an absent cluster and refuses a collision. On a genuinely fresh lab, create the private directories, empty acceptance config, and empty 0600 kubeconfig placeholder without replacing an existing file:

```bash
install -d -m 0700 /tmp/keaguard-m2-acceptance
install -d -m 0700 /tmp/keaguard-m2-acceptance/docker-config
test -z "$(find /tmp/keaguard-m2-acceptance/docker-config -mindepth 1 -print -quit)"
KUBECONFIG=/tmp/keaguard-m2-acceptance/keaguard-kind.kubeconfig
if [ ! -e "$KUBECONFIG" ]; then install -m 0600 /dev/null "$KUBECONFIG"; fi
test -f "$KUBECONFIG" && test ! -L "$KUBECONFIG"
test "$(stat -c '%a' "$KUBECONFIG")" = 600
```

For all M2 commands, explicitly select the same profile and context:

```bash
export GOTOOLCHAIN=local
export KEAGUARD_E2E_MILESTONE=m2
export KEAGUARD_E2E=1
export KEAGUARD_KIND_CLUSTER=keaguard-m2-disposable
export KEAGUARD_KIND_CONTEXT=kind-keaguard-m2-disposable
export KEAGUARD_E2E_DISPOSABLE=keaguard-m2-disposable
export KUBECONFIG=/tmp/keaguard-m2-acceptance/keaguard-kind.kubeconfig
export DOCKER_CONFIG=/tmp/keaguard-m2-acceptance/docker-config
export IMG
```

Only after current Gate A, image evidence, and empty-kubeconfig checks pass, a fresh lab may be created exactly once:

```bash
make kind-create IMG="$IMG"
```

Namespace provisioning is a separate administrator-controlled, create-only step. It preflights both names and never adopts or relabels an existing namespace. The runtime namespace is `keaguard-m2-runtime` with `enforce=privileged` and `enforce-version=v1.37`; `keaguard-m2-outside` is `enforce=restricted` and `enforce-version=v1.37`. Both are bound to the exact M2 cluster owner label and recorded UID/server/CA/node receipts. Do not copy this example to shared clusters or reuse it to repair a collision. After reviewing that both namespaces are absent in a fresh lab, the guarded one-shot setup command is:

```bash
KEAGUARD_M2_NAMESPACE_SETUP=1 go test ./test/e2e \
  -run '^TestM2NamespaceSetup$' -count=1 -timeout=90s -v
```

The manager ServiceAccount is deliberately weaker than the administrator. Its namespaced Role can create/delete/get/list/patch/watch ConfigMaps, Services, and StatefulSets; get/list/watch Pods; get/list/watch KeaClusters; and patch KeaCluster status. It cannot update these resources, inspect Secrets, alter namespace labels/policy, manage RBAC, or perform cluster-scoped operations. The Operator never changes Pod Security Admission. DHCPv4 explicitly needs `NET_RAW`, which Baseline and Restricted reject; the reviewed privileged policy is an administrator-created lab fixture, not a general production recommendation. Keep it confined to the dedicated disposable runtime namespace and restore the full prior label set after negative tests.

Run admission first, then the complete serial M2 profile. Each command is separately guarded, loads/attests the current fingerprinted image, and leaves the cluster and private evidence in place:

```bash
make test-kind IMG="$IMG" GINKGO_FOCUS='M2: Admission'
make test-kind IMG="$IMG" GINKGO_FOCUS=''
```

The full suite includes the retained `KIND:` regression cases and M2 leaves, including logging `NONE`. Under the reviewed final M2 timing amendment, the full-suite Ginkgo timeout is 70 minutes and the outer Go test timeout is 75 minutes. The nine-minute admission reserve and the per-scenario limits are unchanged, including the 170-second aggregate cleanup limit and the existing restoration, diagnostics, subprocess, output, grace, and body budgets. The amendment applies only to the full M2 acceptance run; M1 timing and focused-suite behavior are unchanged. No focused run, skipped/pending leaf, or previous task's pass substitutes for the unfocused T20 result. M2 runs serially and suppresses the inherited M1 diagnostic/restoration hooks only under this profile; M1 retains its original teardown behavior.

## Workload contract and limitations

- **No DHCP service claim:** generated configurations intentionally contain no interfaces, subnets, pools, hooks, or control sockets. No DHCP listener or packet exchange is enabled. Health checks are process probes, not request handling, allocation, network reachability, or Kea HA health.
- **No HA or shared leases:** the two StatefulSet replicas are independent Kea processes. There is no lease synchronization, active/standby protocol, shared storage, or cross-replica DUID protocol. Do not describe replicas as a failover pair.
- **Ephemeral state:** same-Pod container restart keeps that Pod's `emptyDir` data, including its DHCPv6 DUID. Pod replacement, rollout, disable, or node loss can discard that data; a new Pod gets new ephemeral state/DUID. No persistence across those transitions is promised.
- **Rollout behavior:** the controller uses native StatefulSet ordering/readiness and reports pending/stalled desired state honestly. It does not force rollback, bypass admission, or claim a successful service merely because the Deployment or Pod is Ready.
- **Security:** containers are non-privileged, run as UID/GID 100/101, use a read-only root filesystem, RuntimeDefault seccomp, no privilege escalation, drop `ALL`, and add only the family-specific approved capabilities. DHCPv4 adds `NET_BIND_SERVICE` and `NET_RAW`; DHCPv6 adds only `NET_BIND_SERVICE`. Never add capabilities, use alternate images, or weaken these guards to pass admission.
- **Disable vs deletion:** to disable, explicitly set `spec.workload.enabled` false and wait for observed disabled status and owned workload cleanup. For example, with the explicit M2 kubeconfig/context:

  ```bash
  kubectl --kubeconfig "$KUBECONFIG" --context "$KEAGUARD_KIND_CONTEXT" \
    -n keaguard-m2-runtime patch keacluster keacluster-m2-sample \
    --type=merge -p '{"spec":{"workload":{"enabled":false}}}'
  kubectl --kubeconfig "$KUBECONFIG" --context "$KEAGUARD_KIND_CONTEXT" \
    -n keaguard-m2-runtime get keacluster keacluster-m2-sample -o yaml
  ```

  Deleting the parent is a separate Kubernetes garbage-collection action, not the disable workflow. GC is asynchronous and can be blocked by additional owners, orphan propagation, finalizers, or missing owner references. Do not strip unknown finalizers or delete foreign resources.
- **Ownership and recovery:** the controller does not adopt conflicting same-name or foreign resources. Investigate exact GVK/name/UID/owner references and the private scenario ledger. Conflicts, missing permissions, immutable config, stale UIDs/resourceVersions, and unresolved API outcomes may block safely. Each invasive test must complete UID/owner-verified restoration and seal its restoration receipt before bounded diagnostics; diagnostics have a separate status and cannot prove restoration. A recovery marker blocks the next invasive run. Reconcile only the exact recorded identities; never infer success from a missing object or a command exit alone.
- **Lab lifetime:** the acceptance suite does not delete namespaces or the Kind cluster, run Docker prune, or clean global Docker credentials. Retain the dedicated cluster and private evidence for review. Cluster disposal requires separate explicit authorization.

Use the disabled-by-default M1 sample for metadata-only reconciliation. Apply [the M2 sample](../../config/samples/infrastructure_v1alpha1_keacluster_m2.yaml) only as an explicit opt-in after the dedicated lab and manager are ready; disable it explicitly before separately testing parent deletion/GC.
