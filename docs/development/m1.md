# M1 development and local acceptance

M1 is an internal Kubernetes reconciliation foundation. A `KeaCluster` has an intentionally empty `spec`; the controller creates or repairs one namespaced ConfigMap containing the resource's name, namespace, and UID. The ConfigMap is an ownership/reconciliation artifact, not a Kea configuration. `ArtifactReconciled=True` means that this artifact matched the observed ownership and managed fields at reconciliation time. It says nothing about Kea, DHCP packets, lease synchronization, or service availability.

## Generate, build, and run local checks

From the repository root:

```bash
export GOTOOLCHAIN=local
make toolchain-check
make fmt
make generate manifests
make verify-generated
make vet
make build
make test-unit
make test-envtest
make test-manifests
```

`make test` runs unit and envtest suites; `make test-manifests` is a separate structural rendering check. Envtest starts a local API server and etcd for API/controller integration. It does not model Kubernetes garbage collection. `make docker-build IMG=keaguard-operator:m1-test` builds the pinned Linux/amd64 manager image locally. The default rendered runtime manifest uses that image name; a local Kind node needs the image loaded before applying the runtime manifest.

## Install the API and runtime separately

The CRD installer and runtime composition are deliberately separate. Install the CRD, wait for registration, then apply the runtime bundle. The default runtime namespace is `keaguard-system`.

```bash
kubectl apply -k config/crd
kubectl wait --for=condition=Established crd/keaclusters.infrastructure.keaguard.example --timeout=120s

IMG=keaguard-operator:m1-test
make docker-build IMG="$IMG"
export KEAGUARD_KIND_CLUSTER=your-disposable-kind-cluster
kind load docker-image "$IMG" --name "$KEAGUARD_KIND_CLUSTER"

kubectl apply -k config/default
kubectl -n keaguard-system rollout status deployment/keaguard-controller-manager --timeout=120s
kubectl apply -f config/samples/infrastructure_v1alpha1_keacluster.yaml
kubectl wait --for=condition=ArtifactReconciled=True keacluster/keacluster-sample -n keaguard-system --timeout=120s
kubectl get configmap keacluster-sample -n keaguard-system -o yaml
```

Use an explicitly chosen disposable Kind name in the image-load command. The sample has no Kea workload fields. Its resulting ConfigMap is only the internal artifact described above.

For another runtime namespace, render an outer Kustomize overlay over a copy of `config/` and copy `config/default/namespace_replacement.yaml` beneath the overlay root. Apply `namespace: <chosen-name>` and `replacements: - path: namespace_replacement.yaml` at that outer level. The replacement keeps the Deployment's `--watch-namespace` argument aligned with the rendered namespace; Kustomize's load restrictions remain enabled. The manifest contract tests render two such namespace overlays. Do not change only the Deployment namespace or the flag.

## Runtime identity and permissions

The Deployment runs one manager replica with the `keaguard-controller-manager` ServiceAccount in its runtime namespace. Its namespaced Role grants only:

- ConfigMap: `get`, `list`, `watch`, `create`, `patch`.
- KeaCluster: `get`, `list`, `watch`.
- KeaCluster status: `patch`.

The runtime identity has no ConfigMap delete/update, finalizer, Secret, Namespace, CRD, cluster-scoped, token-request, or event permissions. The administrator who installs the CRD/runtime and prepares test fixtures is a separate identity. Discovery needed by the client libraries is a cluster assumption and is not a grant to reconcile resources outside the watched namespace.

## Guarded Kind acceptance

The ordinary test suite does not create, select, or delete a cluster. Kind creation is a separate, explicit target, and the current acceptance guard is pinned to the disposable cluster `keaguard-m1-disposable`, context `kind-keaguard-m1-disposable`, node-image digest above, and the private kubeconfig path `/tmp/keaguard-m1-t13-lenovo/keaguard-kind.kubeconfig`. It rejects another context or kubeconfig, a symlink/non-private kubeconfig, an unexpected server/CA or node membership, and an unselected/floating image. Never copy credentials into the repository or reuse this acceptance setup against a production/shared cluster.

On a fresh lab only, prepare a private native-Linux directory and an empty task-local Docker configuration. Do not replace a populated kubeconfig or Docker configuration:

```bash
install -d -m 0700 /tmp/keaguard-m1-t13-lenovo
install -d -m 0700 /tmp/keaguard-m1-t13-lenovo/docker-config
test -z "$(find /tmp/keaguard-m1-t13-lenovo/docker-config -mindepth 1 -maxdepth 1 -print -quit)"
KUBECONFIG=/tmp/keaguard-m1-t13-lenovo/keaguard-kind.kubeconfig
if [ ! -e "$KUBECONFIG" ]; then install -m 0600 /dev/null "$KUBECONFIG"; fi
test "$(stat -c '%a' "$KUBECONFIG")" = 600
```

With that fresh, empty kubeconfig and the empty `DOCKER_CONFIG`, explicitly select the lab before the separate creation target:

```bash
export KUBECONFIG=/tmp/keaguard-m1-t13-lenovo/keaguard-kind.kubeconfig
export DOCKER_CONFIG=/tmp/keaguard-m1-t13-lenovo/docker-config
export KEAGUARD_E2E=1
export KEAGUARD_KIND_CLUSTER=keaguard-m1-disposable
export KEAGUARD_KIND_CONTEXT=kind-keaguard-m1-disposable
export KEAGUARD_E2E_DISPOSABLE=keaguard-m1-disposable
export IMG=keaguard-operator:m1-test

make kind-create IMG="$IMG"
```

`make kind-create` refuses to overwrite a populated kubeconfig or create a cluster with the selected name if one already exists. It does not delete a cluster. If the approved disposable cluster already exists, inspect and select it; do not run the creation target.

Run the full live suite only with the same explicit selection and `IMG`:

```bash
make test-kind IMG="$IMG" GINKGO_FOCUS=''
```

Focused examples use `GINKGO_FOCUS='KIND: (Runtime identity|Core|Startup authorization)'` or `GINKGO_FOCUS='KIND: (Restart|Garbage collection|Ownership cleanup limits)'`. A focused pass is not a full-suite result. The suite loads the selected local image and validates the real deployed ServiceAccount with API requests, including expected `Forbidden` results. It leaves the cluster and fixture objects in place; review the selected cluster before any separate cleanup.

## Recovery and operator limitations

- **Ownership conflict:** the controller does not adopt a same-name ConfigMap based on its name or labels. Inspect both objects and their UIDs/owner references. Resolve the conflict administratively; the controller retries observation but does not delete or relabel the conflicting object.
- **Immutable artifact:** `ImmutableArtifact` means Kubernetes will not accept repair. After verifying the exact test/application object, an administrator may remove that artifact so the active parent can receive a newly created mutable artifact. The controller does not remove it or clear immutability.
- **Terminating artifact:** `ArtifactDeleting` means the existing object has a deletion timestamp. Inspect remaining finalizers and the responsible owner before resolving a blocker. The controller does not strip finalizers or recreate over the old UID.
- **Retry behavior:** transient returned errors use controller-runtime's rate limiter (1, 2, 4, 8, 16, 32 seconds, then at most 60 seconds for a key, resetting after success). Healthy observations are revisited every five minutes; observed blockers every 30 seconds. These are scheduling intervals, not recovery guarantees. Permanent validation/permission errors may require administrator correction.
- **Startup failures:** invalid `--watch-namespace` syntax fails closed before reconciliation. Valid namespace syntax is not proof that the Namespace exists or that API access is authorized. A missing/incorrect ServiceAccount binding or forbidden startup/cache request can keep the manager unready. Inspect Deployment arguments, ServiceAccount, Role/RoleBinding, and logs; correct the specific configuration/authorization problem, then verify rollout and a real reconciliation. Do not broaden runtime privileges to make an unrelated error disappear.
- **Concurrent changes:** writes use fresh API state and optimistic resource-version checks; stale parent UID/generation observations are not transferred to a replacement resource. A conflict is re-read on a later pass. If an API write may have committed but its response was lost, the condition can be `Unknown`; the controller re-observes before another mutation. A later status-patch failure does not undo an artifact write that already committed. `observedGeneration` identifies the input generation for the reported observation, including unsuccessful observations. This does not make external mutations immediate or atomic.
- **Restart:** a new manager reconstructs desired artifact state from the API. A restart is not uninterrupted availability; the manager cannot reconcile while stopped and may remain unready if startup configuration or API authorization is still invalid.
- **Garbage collection:** normal Kubernetes owner-reference GC is asynchronous. M1's runtime Role lacks delete permission, so child cleanup is performed by Kubernetes GC, not the manager. Orphan propagation, missing/dangling references, an additional live owner, and a test finalizer change observed outcomes. Do not promise immediate deletion or use the T14 observation as a blanket cleanup guarantee.

## Milestone boundary

M2 must decide how to migrate the internal ConfigMap artifact before adding or replacing it and must design real Kea fields, lifecycle, storage/reload, and status. M3 owns an isolated DHCP relay/packet and native Kea HA lab. Kubernetes NodePort behavior is not evidence of DHCP relay delivery. No M1 test in this repository claims a Kea deployment, DHCP traffic, lease synchronization, failover time, or performance result.
